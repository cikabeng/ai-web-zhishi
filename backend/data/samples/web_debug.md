# Web 前端调试与接口排查笔记（示例课程资料）

> 本文件是项目自制的示例教学资料，用于演示知识库检索与引用。

## 一、先看浏览器控制台

前端出现问题，第一步永远是打开浏览器开发者工具（F12），切到 Console 面板。

控制台里的红色信息通常是 JavaScript 运行时报错，会给出报错类型、消息和文件行号。

常见类型：

- `ReferenceError`：使用了未声明的变量；
- `TypeError`：对一个 `undefined` 或 `null` 取属性，例如 `Cannot read properties of undefined (reading 'name')`；
- `SyntaxError`：语法错误，通常是括号、引号没配对。

读法是从上往下看第一条红色错误，因为后面的错误往往是第一条导致的连锁反应。

## 二、再看 Network 面板

如果页面能打开但数据不对，问题通常在网络请求。

在 Network 面板按 Fetch/XHR 过滤，找到失败的请求，依次检查：

1. 请求 URL 是否正确（是否少了前缀、是否拼错路径）；
2. 请求方法是否正确（GET 与 POST 不能混用）；
3. 请求体字段名是否和后端一致；
4. 响应状态码是多少；
5. 响应体里的错误信息写了什么。

状态码速查：

- `400`：请求参数不合法，通常是字段缺失或类型不对；
- `401 / 403`：未登录或没有权限；
- `404`：路径错误或资源不存在；
- `422`：参数校验失败，后端通常会说明哪个字段不合法；
- `500`：后端内部错误，需要看后端日志。

## 三、CORS 是什么

CORS（跨域资源共享）是浏览器的安全机制：当前端页面和接口不在同一个"源"（协议 + 域名 + 端口）时，浏览器会拦截响应，除非服务端明确允许。

典型表现是控制台出现类似 "blocked by CORS policy" 的报错，而 Network 里请求其实已经发出了。

排查要点：

- 确认后端是否返回了 `Access-Control-Allow-Origin` 响应头；
- 确认该头的值是否包含前端的源，不能同时使用 `*` 和携带凭证的模式；
- 预检请求（OPTIONS）是否被后端正确处理。

开发阶段的常见做法是用开发服务器代理：前端把 `/api` 请求代理到后端，浏览器看到的始终是同源请求，就不存在跨域问题。

## 四、前端报错与后端报错怎么区分

如果 Network 里请求状态是 200，但页面仍然报错，问题多半在前端的数据处理逻辑。

如果请求状态是 4xx 或 5xx，问题在后端或请求本身，前端只是把错误显示出来。

如果请求根本没出现在 Network 里，说明代码在发请求之前就出错了，回到 Console 找第一条错误。

## 五、排查顺序建议

1. 复现问题，记录完整操作路径；
2. 打开 Console，读第一条错误；
3. 打开 Network，找到对应请求，看状态码与响应体；
4. 对照接口文档检查字段名与类型；
5. 用最小请求（例如只带一个字段）验证接口是否正常；
6. 确认是数据问题、协议问题还是渲染问题。
